# docs/design/frontend-abstraction-plan-v2.md — 前端抽象复核与修订方案

> **状态：修订稿，撤回上一版《前端组件抽取方案》，未改代码。**
> **结论先行**：上一版提出的 13 个组件**全部不做**；只保留 6 个真正"同一规则多处实现"的去重项；历史详情、表单容器、状态展示这类会改变用户习惯的调整，从重构中剥离，单独立项、单独确认。
> **基线**：v4.19.2（`8d70366`），`frontend/src` 实读。
> **上一版**：[frontend-component-extraction-plan.md](frontend-component-extraction-plan.md)（已标注撤回，仅作评审记录）。

---

## 0. 结论

| 项 | 上一版 | 本版 |
|----|--------|------|
| 新增 UI 组件 | 13 个 | **0 个** |
| 新增组合式函数 | 9 个 | **2 个（条件性）** |
| 新增工具模块 | 2 个 | **1 个 + 2 个既有文件追加** |
| 共享样式 | 无（靠组件承载） | **2 个 SCSS partial** |
| 新增文件总数 | 20+ | **≤6** |
| 交互/视觉变更 | 混在 P1–P3 | **全部移出，单独立项** |
| 验收口径 | 行数下降 | **同一规则实现份数 = 1；模板与视觉零变化** |

**一句话**：这份方案只做"把同一条知识从多处收回一处"，不做"把相似的界面装进同一个组件"。

## 1. 上一版错在哪（逐条回应）

### 1.1 为组件化而组件化：中间商组件是负资产

上一版列的 `EntityFormDrawer`、`ConfigSectionCard`、`ExecPanel`、`SettingRow`、`ParamBlock`，本质都是给 Element Plus 或一个 div 套壳，然后把 `modelValue / title / size / saving` 原样转发，再开两个插槽。

定义一个**中间商组件**：删掉它，调用方需要多写 3–10 行模板；保留它，调用方需要多读一份 props/events/slots 契约，并且每次 Element Plus 升级都要检查转发是否漏项。**它没有让调用方少理解任何概念。**

判据只有一句：

> 抽取后，调用方是否**少理解一个概念、少写一段代码**？如果只是把代码搬到另一个文件，不算。

按此判据，上一版 13 个组件里，至少 7 个是中间商。

### 1.2 抽象没有消除重复，只是把重复搬了家

上一版声称"四组结构性重复"，但落地后：

- 业务编排（选哪些任务、参数如何映射、启动后跳哪）仍在三个页面各写一遍；
- 筛选状态、轮询语义、错误处理仍各自保留；
- 真正被消除的主要是 CSS 与骨架；
- 代价是新增 4 套目录、20+ 文件、props 契约与插槽协议，**阅读路径变长**。

这是用"结构相似"冒充"知识重复"。结构相似的正确解法通常是**共享样式**，不是共享组件。

### 1.3 把交互变更伪装成"纯重构"

上一版把三件事和纯逻辑收敛混在同一张优先级表里：

| 项 | 实际性质 | 影响 |
|----|----------|------|
| D3 历史统一抽屉 | 交互变更 | 调度/上传用户从"页内详情"改为抽屉，返回路径变化 |
| D4 弹窗统一抽屉 | 交互变更 | 调度/命名规则的新建编辑从弹窗变侧滑 |
| D5 状态组件合并 | 视觉 + 语义变更 | 7 个页面的状态从"点 + 文字"变成胶囊，密度与扫视节奏变化 |

这些都不是重构，是产品决策。混在一起会导致：无法用"截图 diff = 0"验收，出问题也说不清是重构引入还是交互调整引入。

### 1.4 缺少删除标准与失败判据

上一版只有"行数目标"，没有回答：

- 什么时候应该**删掉**一个抽象？
- 什么情况下判定"这次抽象失败了"？
- 谁在过程中有权否决？

行数下降不是结构改善的证据——把代码搬进组件文件同样能让页面变短。

### 1.5 可复用性判断错误

上一版把真正有价值的纯函数（格式化、日期边界）放在 P0，体量很小；把风险最高、收益最低的大组件抽取放在 P1–P3。这是优先级倒置。

## 2. 复核数据：把上一版的夸大纠正

写方案前重新用代码核对了一遍，以下数字与上一版不同，以本节为准：

| 项 | 上一版说法 | 实测 | 差异原因 |
|----|-----------|------|----------|
| 客户端分页 | 5 处 | **4 处**（TaskManage、RenameRules、调度历史、上传历史） | 自动化历史是服务端分页 |
| 日期边界转换 | 6 处 | **2 处**（调度历史、上传历史） | 自动化直接把 `YYYY-MM-DD` 传给后端；其余是注释 |
| 执行启动时序 | 3 页同构 | **2 页同构**（调度、上传）；自动化走 `start/batchStart` 并跳 `task_id` | 自动化根本没有"先建记录再连日志启动"的链路 |
| 选择逻辑 | 3 处同规则 | **3 处、2 种锁模型** | 调度/自动化按任务锁；上传用全局 `executing` 闸门 |
| 轮询 | 15 处同一模式 | **15 个定时器、3 类语义**（轮询取数 / 计时刷新 / WS 看门狗） | 不能合成一个 API |
| 打开日志目录 | 14 处重复 | **3 个函数定义、14 个引用** | 引用里多数是模板按钮，真正的重复是 3 份 3 行封装 |
| 状态展示 | 两套组件 | **属实**：`StatusDot` 7 页、`StatusPill` 2 页 | 但这是视觉变更，见第 6 节 |

**结论**：上一版把"看起来像"当成了"是同一件事"。真正同规则的重复比声称的少，且集中在无 UI 的逻辑层。

## 3. 判断标准（先定尺子）

### 3.1 三种重复，只有一种值得抽代码

| 类型 | 定义 | 例子 | 处置 |
|------|------|------|------|
| **知识重复** | 同一条规则在多处实现，改一处必须改另一处 | `countText` 的 0/0 → `—`；北京时间日界 | 抽纯函数/组合式 |
| **结构相似** | 长相像，但语义、生命周期、数据形状不同 | 三个执行页的三栏布局 | 共享样式，不共享组件 |
| **视觉一致** | 看起来应该一样，但实现可以各自独立 | 卡片圆角、状态颜色 | 用令牌/样式统一，不抽组件 |

### 3.2 抽取净收益（定性公式）

```
净收益 ≈ 消除的实现份数 × 该规则的变更频率
        − 新增契约数（props/events/slots/options） × 阅读成本
```

- 份数 < 3：不抽（2 处重复的维护成本低于一份契约）。
- 规则几乎不变更：不抽（例如一次性的页面布局）。
- 需要 3 个以上 option 才能覆盖现有差异：判定"不是同一条规则"，不抽。
- 抽取后调用方模板没有变短：判定为搬运，撤销。

### 3.3 组件的门槛比函数高得多

组件只有在**减少概念**时才值得存在。以下情况一律不抽组件：

1. 只是转发第三方组件的 props/slots；
2. 只服务于一个页面；
3. 需要靠 `variant` / `mode` 等开关适配两个以上页面的差异；
4. 抽取后，页面仍需自己组织同样的业务顺序。

## 4. 建议做的 6 件事

> 全部属于"知识重复"，不改变任何行为与视觉。新增文件 ≤6，新增 UI 组件 0。

### 4.1 `utils/format.ts`（新增，1 个文件）

**消除的重复**

| 函数 | 处数 | 现状 |
|------|------|------|
| `countText(success, total)` | 3 | 三处实现逐字相同：`total > 0 ? 's/t' : '—'` |
| `triggerText(row)` | 4 | 四处实现逐字相同：`automation` → `自动化 · 名称`，否则 `手动` |
| `matchKeyword(fields, keyword)` | 19 处表达式 / 12 个文件 | 各写一遍 `toLowerCase().includes`，字段列表不同 |
| `durationHuman(sec)` | 2 | `4 分 12 秒`（列表/记录用） |
| `durationClock(sec)` | 1 | `04:12`（监控页计时用） |

**关键设计：两种耗时格式不合并。** 它们服务不同场景（记录页要"人话"，监控页要"计时器"），合并会改变其中一处的显示。抽成两个命名函数，行为逐字保持。

```ts
function countText(success: number, total: number): string
function triggerText(row: { trigger_source?: string | null; trigger_name?: string | null }): string
function matchKeyword(fields: Array<string | null | undefined>, keyword: string): boolean
function durationHuman(seconds: number | null): string   // 4 分 12 秒
function durationClock(seconds: number): string          // 04:12
```

**不消除什么**：各页的关键字输入框、筛选条件组合、空态文案仍留在页面。

**风险**：低。唯一需要注意的是 `matchKeyword` 的字段顺序与大小写行为，必须与现有 19 处一致；抽完用逐页对照验证。

**验收**：`grep -c "toLowerCase().includes"` 从 19 降到 0（保留函数内部 1 处）。

### 4.2 `utils/date.ts` 追加 `dayRangeMillis`（不新增文件）

**消除的重复**：调度历史、上传历史各写一遍：

```ts
start: beijingMillis(`${range[0]} 00:00:00`)
end:   beijingMillis(`${range[1]} 23:59:59`)
```

**不消除什么**：自动化历史把日期原样传给后端，不参与此函数——这是两套语义，不能合并。

```ts
function dayRangeMillis(range: [string, string] | null): { start: number | null; end: number | null }
```

**风险**：低。注意入参是 `YYYY-MM-DD`，返回值是毫秒；空范围返回 `{ start: null, end: null }`。

### 4.3 `api/desktop.ts` 追加 `openLogDirSafe`（不新增文件）

**消除的重复**：三个历史页各有：

```ts
desktopApi.openLogDir('openlist').catch(() => { /* 拦截器提示 */ })
```

差异只有一个字符串参数。

```ts
function openLogDirSafe(kind: 'openlist' | 'upload' | 'automation'): Promise<void>
```

**不消除什么**：按钮位置、图标、文案留在页面。

**收益边界**：只省 3 份 3 行封装，价值有限；列在这里是因为它同时也是"调用约定"（错误交给拦截器，不重复提示）。如果评审认为不值得，可删掉此项，不伤主线。

### 4.4 `composables/useClientPagination.ts`（新增，1 个文件）

**消除的重复**：4 个页面各写 `page / pageSize / PAGE_SIZES / slice`。算法完全相同：

```ts
const start = (page - 1) * pageSize
return list.slice(start, start + pageSize)
```

```ts
function useClientPagination<T>(source: MaybeRef<T[]>, options?: {
  pageSize?: number          // 默认 20
  sizes?: number[]           // 默认 [10, 20, 50]
}): {
  page: Ref<number>
  pageSize: Ref<number>
  sizes: number[]
  pagedItems: ComputedRef<T[]>
  total: ComputedRef<number>
  reset: () => void
  clampPage: () => void      // 数据变少时收敛页码
}
```

**关键设计：不接管 watch。**

四个页面的"回到第 1 页"时机各不相同：

- `TaskManage`：只有每页条数变化时回第 1 页；
- 调度历史：`keyword / dateRange / statusFilter` 变化时回第 1 页，条数由独立 handler 处理；
- 上传历史：`keyword / statusFilter / dateRange / pageSize` 一起监听；
- `RenameRules`：`keyword / pageSize`，另有"数据变少时收敛页码"。

组合式只提供 `reset` 与 `clampPage`，**由页面自己决定何时调用**。这样抽取不改变任何现有行为，也避免为了兼容差异加 options。

**不消除什么**：筛选条件、分页组件布局、空态。

**风险**：低。禁止在 composable 内 `watch` 业务字段。

### 4.5 `composables/useIdSelection.ts`（新增，条件性）

**消除的重复**：三个执行页各写选中集合、全选、移除、清空（每页约 30–40 行）。

```ts
function useIdSelection(): {
  selectedIds: Ref<number[]>
  isSelected: (id: number) => boolean
  toggle: (id: number) => void
  remove: (id: number) => void
  clear: () => void
  merge: (ids: number[]) => void        // 全选
  removeMany: (ids: number[]) => void   // 取消全选
}
```

**关键设计：只做集合操作，不判断"能不能选"。**

现状有两种锁模型：

- 调度/自动化：`isLocked(taskId)`，执行中的任务不可选；
- 上传：全局 `executing` 闸门，执行期间所有操作不可用。

如果把锁判断塞进组合式，需要 `isLocked`、`canMutate` 两个回调，再加"全选是否包含锁定项"的开关——参数超过 3 个，按本方案自己的标准就应判定"不是同一条规则"。

因此：**组合式只管集合，`if (isLocked(id)) return` 留在页面**。这样三页行为逐字不变，重复的只是集合操作那一小段（约 20 行）。

**条件**：如果评审认为"只省 20 行 ×3，不值得新增一个文件"，可以不做；它不影响 4.1–4.4 与 4.6。

### 4.6 共享样式：`styles/_exec-panels.scss`、`styles/_log-monitor.scss`（2 个文件）

这是本方案里**收益最大、争议最小**的一项：重复的是 CSS，就用样式表去重，而不是造组件。

**证据（逐字比对）**

| 选择器 | 调度 | 上传 | 自动化 | 结论 |
|--------|------|------|--------|------|
| `.exec-workspace` | 232 字符 | 232 | 232 | **三份逐字相同** |
| `.exec-panel` | 1553 | 1553 | 1648 | 前两份逐字相同，自动化多一段 |
| `.log-toolbar` | 256 | 256 | 256 | **三份逐字相同** |
| `.progress-card` | 986 | 986 | 1126 | 前两份相同，自动化多一段 |
| `.realtime-page` | 有 | **无** | 有 | 上传页根类名缺失，属历史漂移 |

**做法**

1. 把三页共用的骨架规则移入 `_exec-panels.scss`：`.exec-page / .exec-body / .exec-workspace / .exec-panel / .task-row / .selected-list / .param-block`；
2. 各页在 `<style scoped lang="scss">` 顶部 `@use '@/styles/exec-panels';`；
3. 模块特有规则（自动化的批量栏、时间参数、上传的冲突策略说明）留在页面；
4. 上传运行详情页补回 `.realtime-page` 根类，或在 partial 里用 `.upload-realtime` 兼容——**这是一个视觉修复，需单独确认**，不混在去重里。

**为什么用 `@use` 而不是全局样式表**：放在 scoped style 内，编译后仍带该组件的作用域属性，**不会泄漏到其他页面**；代价是每个组件打包一份 CSS（体积不降），收益是**源码只有一份**。本项目的目标是可维护性，不是压缩产物。

**风险**：CSS 顺序与优先级变化可能带来细微视觉差异。缓解：迁移前后各页截图逐像素比对；自动化页多出的规则单独保留，不并入 partial。

**验收**：三个执行页的 `<style>` 中不再出现 `.exec-panel` 等骨架定义；`_exec-panels.scss` 行数约为原三份之和的 1/3；截图 diff = 0。

## 5. 明确不做

### 5.1 上一版 13 个组件全部不做

| 组件 | 不做的理由 |
|------|-----------|
| `EntityFormDrawer` | 转发 `el-drawer`，中间商 |
| `ConfigSectionCard` | 转发卡片容器，中间商 |
| `ExecPanel` | 只承载样式；改用 SCSS partial 后无存在必要 |
| `SettingRow` | 一行布局，抽了反而增加一层 |
| `ParamBlock` | label + 控件 + 说明，模板只省 3 行 |
| `StatusBadge` | 合并会改变 7 个页面的视觉，属 B 类变更（见第 6 节） |
| `ExecutionWorkbench` | 纯布局；三页差异靠 slot 传，契约成本高于收益 |
| `TaskPickerPanel` | 泛型 + 插槽 + 5 个 props，调用方模板并未变短 |
| `SelectedTasksPanel` | 同上；三页摘要文案与主按钮语义不同 |
| `RunningExecutionsTable` | 列配置 + 插槽，等于自己造了一个表格框架 |
| `LogMonitorLayout` | 统计项数量与语义不同，靠 `stats` 数组硬凑 |
| `LogFilterBar` | 三页逻辑相近但可共享样式；抽组件收益低于 partial |
| `LogDrawer` | 只服务历史页，且各页 loader 不同 |

### 5.2 其他不做

- **目录重构**（`components/execution|log|history`）：没有组件要放，不建空目录。
- **启动时序 composable**：只有调度/上传 2 处，且自动化模型不同；2 处不值得一份契约。
- **`useLogStream` / `useEntityForm` / `useConfirmAction`**：分别受帧结构差异、字段差异、文案差异影响，抽取后需要大量 options 或插槽，判定为"结构相似"。
- **确认弹窗统一**：18 处文案与危险级别不同，统一外壳只省 2 行；真正需要统一的是文案规范，属产品文档，不是代码抽象。

## 6. 变更隔离：A / B / C 三类，不混做

| 类别 | 定义 | 本方案 | 发布 | 需要谁确认 | 验收方式 |
|------|------|--------|------|-----------|----------|
| **A 纯去重** | 不改行为、不改视觉、不改交互 | ✅ 第 4 节全部 | PATCH | 代码评审 | 截图 diff = 0 + 行为清单 |
| **B 视觉统一** | 视觉变化，交互不变 | ❌ 另立项 | PATCH | 设计确认 | 视觉评审 + 截图 |
| **C 交互变更** | 操作路径/习惯变化 | ❌ 另立项 | MINOR | **用户确认** | 交互走查 + 使用验证 |

**B 类候选**（本方案不实施）

1. 状态展示合并（`StatusDot` 7 页 + `StatusPill` 2 页 → 一套）：会改变表格内状态的字号、底色、行高观感。
2. 运行详情页补齐 `.realtime-page` 根类：会让上传页的间距/滚动行为与另两页一致（可能正是期望，但仍是视觉变化）。

**C 类候选**（本方案不实施，需逐项确认）

1. 运行记录详情：调度/上传是页内切换，自动化是抽屉。统一成哪种？会改变返回路径与"看详情"的手感。
2. 新建/编辑容器：调度用弹窗、上传混用、自动化用抽屉。统一成抽屉还是弹窗？影响表单填写时的上下文可见性。

> 这两项在上一版被写成"纯重构"，是错误的。它们各自需要一次产品确认、一次独立版本，不能夹带在去重 PR 里。

## 7. 删除与失败判据

### 7.1 什么情况下删掉一个抽象

| 条件 | 判定 | 处置 |
|------|------|------|
| 上线 30 天后调用点 < 3 | 复用假设不成立 | 删除，实现退回调用方 |
| 为适配某个页面新增了只服务 1 处的 option | 抽象开始腐化 | 删除该 option；若无法删除，整体回退 |
| option 数量 > 3 | 不是同一条规则 | 回退为就地实现 |
| 调用方模板/脚本没有净减少 | 只是搬运 | 回退 |
| 需要 2 个以上插槽才能覆盖现有场景 | 结构相似而非知识重复 | 回退 |
| CSS partial 需要页面 override 超过 20% | 骨架并不共用 | 拆回页面 |

### 7.2 什么算"这次抽象失败"

- 迁移后出现任何**无法用截图 diff 解释**的行为差异；
- 需要修改产品文案/交互才能让抽象成立；
- 为一个页面加了 `if (isXxx)` 分支；
- 新人阅读页面时需要先读组件才能看懂业务流程（阅读路径变长）。

出现任一条，停止推广，保留已验证的部分，其余回退。

### 7.3 验收指标（替代"行数下降"）

| 指标 | 合格线 |
|------|--------|
| 同一规则的实现份数 | 1（`grep` 可证） |
| 新增 UI 组件 | 0 |
| 新增 props/events/slots 契约 | 0 |
| 页面模板 diff | 仅 import 行 |
| 视觉 diff | 0（逐像素） |
| 新增文件 | ≤ 6 |
| 行为差异 | 0，逐条对照 |

- 每一步独立提交，commit 里必须出现"删除的重复实现"；
- 页面模板只允许改 import 与调用，不允许改结构；
- 任一步出现视觉差异，先停下来判断是不是 CSS 顺序问题，不允许"顺手调一下"。

- 新增文件 ≤6，新增 UI 组件 0；

- 页面模板改动：0 处结构变化；
- 视觉变化：0。

## 9. 什么情况下才值得组件化（前置条件）

不是永远不抽组件，而是门槛要高。同时满足以下四条才立项：

1. **三个以上模块的交互完全一致**，不是"长得像"；
2. **产品已确认统一**，有书面行为规格（含空态、错误、键盘）；
3. 现有代码无法用"函数 / 样式 / 数据"解决，确实需要共享 DOM 结构；
4. 抽取后调用方**少理解一个概念**，而不只是少写几行。

不满足任一条，就用函数、样式或直接复制。复制的成本是可见的；错误抽象的成本是长期的。

## 附录 C：术语

- **知识重复**：同一条规则在多处实现，改一处必须改另一处。
